# 开发工作流

> **状态**：权威
> **读取时机**：开始一批工作、提交或汇报之前

## 分批

- 工作按批推进，每批对应 [路线图](../roadmap.md) 的一项或其中一部分，能独立验证。
- 每批开始和结束各计算一次四份 CLI 配置文件的 SHA-256，有变化要说明来源：

```bash
shasum -a 256 ~/.claude/settings.json ~/.codex/config.toml ~/.pi/agent/settings.json ~/.pi/agent/models.json
```

- 每批完成并汇报后，等用户确认再开始下一批。

## 分支和提交

- 个人项目，默认在 `main` 上工作。较大或有风险的改动用分支。
- 只在用户要求时提交和推送，不改写已推送的历史。
- 提交信息用英文：第一行概括，正文写改了什么和遗留问题。
- 提交前 `pnpm typecheck`、`pnpm test`、`cargo test` 都要通过。

## 决策和文档

- 影响方向的决定写进 [决策记录](../decisions.md)，包括日期、结论和原因。拿不准的写进待定项，不要默认替用户决定。
- 规则变了就同一批改文档。文档只写现状，计划写进路线图。

## Review 严重度

| 等级 | 含义 | 处理 |
|---|---|---|
| P0 | 丢数据、改写用户配置、安全问题、上报 | 必须修，不能提交 |
| P1 | 主要功能坏了，或违反产品原则 | 必须修 |
| P2 | 边缘情况、可维护性 | 修或写进路线图 |

## 汇报

每批完成后说明：

1. 改了什么；
2. 实际跑的命令和结果数字；
3. 保留或拿不准的部分，以及原因；
4. 对启动和内存的影响；
5. 下一批需要知道的事。

没验证过的不要说成已完成。界面和文案默认用中文，文档用中性措辞，写“用户自己安装的 CLI”。
