# CI 自动化补齐验收

日期：2026-11-06。范围：常规 CI、Pages 发布门禁、容器启动验收、`latest` 晋升与本地验证入口。源码目录保持原状，改动保留在工作区，尚未提交或发布。

## 四项修正

1. 新增 `ci.yml`，相关改动进入 main 或提交 PR 时运行验证；中转发布通过 `workflow_call` 复用检查。
2. Pages 上传产物前执行共享入口，覆盖根路径、官网子路径的协议浏览器回归及安装、离线、跳转检查。
3. 镜像发布先加载 amd64 产物并启动验收，成功后再构建和推送双架构版本／SHA 标签。本机 `--image` 使用当前架构和独立临时 builder。
4. metadata-action 关闭自动 `latest`。独立晋升任务串行排队，读取现有镜像的版本标签；正式新版本按数字段比较后才更新。旧版本、同版本、预发布及 GHCR 读取失败均保留原 `latest`。

本地从仓库根目录运行 `node .github/scripts/verify.mjs`，追加 `--image` 验证容器；命令、依赖和边界见 [CI 与本地验证](../dev-rules/ci-validation.md)。脚本不执行推送或部署。`pwa/`、`relay/`、`site/` 继续独立安装和构建，没有新增运行依赖。

## 第一轮：业务逻辑审查

核对了常规提交与发布触发范围、依赖路径、浏览器检查与产物上传的顺序、容器检查失败时的发布门禁、手动分支构建、预发布标签和 `latest` 的版本比较。GHCR 404 仅在读取 `latest` 时表示首次发布；准入、权限、服务错误和无法识别的既有版本均停止晋升。

核对了本机动态端口、独立数据卷、配对持久化和退出生命周期。复审发现 CLI 被中断时，Docker 可能已经完成资源创建但尚未返回 ID；清理改为按预留的唯一名称查询实际资源，并在子进程退出后继续清理。新增用例模拟容器和卷创建期间的中断，验证资源回收。

## 第二轮：代码设计审查

验证编排、容器生命周期和版本晋升分别由独立脚本承担，进程工具统一使用参数数组。构建与测试命令由 CI 和本地共用；发布任务按所需范围授予 GHCR 写权限。

复审修正了可复用工作流的输入判断：被调用工作流保留调用方事件，使用显式布尔输入决定是否重复执行容器构建。信号处理等待子进程完成自身清理，资源回收查询使用本轮唯一名称。范围内的已知阻塞问题已处理，并重新执行相关验证。

## 清理与验证边界

本轮浏览器、中转和测试服务已退出；测试容器、命名卷、镜像和独立 Buildx builder 已移除。按执行前基线清理本轮恢复的 PWA／relay 依赖、前端构建、临时 Rust target、截图和临时 actionlint。原有官网开发服务、依赖与其他会话的构建目录保留。测试使用独立浏览器上下文和 fake-host，未读取或修改用户 CLI 配置，未改动用户的 `remote.json` 或 localStorage。

本轮只修改自动化和工程文档，未调整产品运行时代码；启动耗时和常驻内存未复测。

未执行真实 GitHub Actions、GHCR 登录／推送／晋升或 Pages 部署，amd64 容器尚待 CI runner 验收；本机完成的是原生 arm64 验收。版本晋升的 registry 响应与推送边界使用隔离替身测试。真机安装、iOS、公网 WSS 和真实桌面互通沿用既有验证边界，本轮未重跑。
