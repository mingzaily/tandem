### 存储和生命周期

- `queues/<taskId>.json` 保存待发送条目、`inFlight` 和选项；图片保存在 `queues/images/<taskId>/<attachmentId>`。图片文件按 UUID 标识，写入后保持不变。
- 保存先写图片，再原子替换元数据。编辑和排序只写小型 JSON；收到 CLI 接收确认后清理条目和无人引用的图片。队列清空后删除 JSON 和图片目录。
- 旧内联图片加载时迁移；迁移失败保留有效旧文件并暂停对应队列，其他任务继续可用。隔离为 `.corrupt` 的队列保留图片，以便人工恢复；删除隔离文件并重启后可清理其图片。
- 首次入队中断产生的孤立图片目录在下次加载清理。图片清理错误通过 `queue-error` 提示，健康队列继续工作。
- 队列预览使用本地 `queue-image://localhost/<taskId>/<attachmentId>`。后端校验两个 UUID，只读取队列图片目录，按实际图片字节返回媒体类型，并使用 `Cache-Control: no-store`。读取留在阻塞线程。
- 发送前读取当前条目的图片并准备 CLI 内容；读取失败恢复队首并暂停。草稿内存 ID 的释放边界继续是成功持久化入队。
- 当前发送条目的消息气泡使用这次准备过程生成的独立 data URL 预览，接收确认后继续可读；待发送列表使用文件 URL。两者分别遵循发送中消息与待发送草稿的生命周期。
- 桌面 `answer_request` 返回带 `code`、`message` 的错误；手机端现有调用保留字符串错误和原协议。请求是否已结束由后端在与回答相同的锁内判断。

### 20 张图片的写入开销

使用 20 张不同的有效 PNG，每张严格为 5,242,880 字节：1280×1024 随机 RGB 图片，尾部补齐到指定文件大小。总原始图片 100MiB；图片尺寸用于控制字节测试，完整高分辨率解码压力另测。

同一 release 优化等级下，通过 Store 执行入队、加载、编辑和排序。加载各测一次，编辑和排序各三次取中位数；计时包含元数据写入、文件同步和图片清理扫描。

复测入口：在临时目录准备 `0.png` 到 `19.png`，设置 `TANDEM_QUEUE_BENCH_DIR` 为该目录、`TANDEM_QUEUE_BENCH_OUT` 为结果 JSON 路径，然后运行 `cargo test --release queue::tests::measure_large_image_queue_operations -- --ignored --nocapture`。测量使用自己的临时 Store 并在结束时清理。

| 指标 | 修复前内联 JSON | 修复后独立图片 |
|---|---:|---:|
| 总磁盘数据 | 139,816,401 B（133.34MiB） | 104,863,141 B（100MiB 图片 + 5,541B 元数据） |
| 加载 | 86.74ms | 0.19ms |

完整采样值、进程拆分与队列操作数据见 [performance.json](assets/final-review/performance.json)。本批没有测量瞬时内存峰值、20 张图片全部展开的解码占用、单次发送全部图片的协议缓冲，或 100MiB 旧队列首次迁移时的峰值。
